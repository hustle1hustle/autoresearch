# 02 — Target Selection for REP (zkTLS / TLSNotary proofs)

**Scope:** Rank launch targets by `(graph-enrichment value) × (1 / friction to mint)`. Score each on Auth-friction, Data-extraction, Bot-defense, Proof-Value (1–5; 5 = easiest/best/most valuable). Identify the **actual endpoint** carrying each fact and whether **proxy-mode's datacenter verifier-IP** survives the target's bot defense (else MPC or residential proxy is forced).
**Date:** June 2026. **Method:** WebSearch + WebFetch + GitHub. Reclaim/Primus used as "proven-doable" evidence. Every non-obvious claim cites a URL or is tagged ASSUMPTION.

> **How to read "Proxy-mode IP OK?"**: In TLSNotary proxy mode the verifier/attestor opens the TCP socket and forwards encrypted bytes, so **the target server sees the verifier's (datacenter) IP**. "Y" = endpoint tolerates datacenter IPs (public/dev APIs, no aggressive WAF). "N" = datacenter IPs are reputation-blocked or device-attestation gates the endpoint → must use **MPC mode (user residential/mobile IP, ~3–15s)** or route the verifier through a **residential proxy** (weakens trust). "Conditional" = usually fine but rate-limit/WAF risk under load. Reclaim's whole architecture is built around routing through residential connections precisely because "E-commerce platforms maintain databases of known datacenter IP ranges; AWS/GCP/DigitalOcean get flagged and blocked instantly" ([plainproxies](https://plainproxies.com/blog/residential-proxies/how-residential-proxies-help-bypass), [Reclaim "Proxying Is Enough"](https://blog.reclaimprotocol.org/posts/proxying-is-enough)).

## 2. Tier-1 target deep-dives — endpoint evidence + IP/bot-defense verdict

### GitHub — endpoint confirmed, proxy mode works. **(Best launch target.)**
Fact lives in JSON: `POST https://api.github.com/graphql` with `user(login:$u){contributionsCollection(from,to){contributionCalendar{totalContributions}}}`; auth = `Authorization: Bearer <token>` with `read:user` scope ([medium](https://medium.com/@yuichkun/how-to-retrieve-contribution-graph-data-from-the-github-api-dc3a151b4af), [community discussion #77967](https://github.com/orgs/community/discussions/77967)). The same calendar is also embedded in the public profile HTML (`table.js-calendar-graph-table` with `data-count`/`data-date` cells), so an unauthenticated HTML fallback exists, but Reclaim's lesson says prefer JSON. **api.github.com is a public, rate-limited (5,000 req/hr authenticated) API with no Cloudflare interstitial and no datacenter-IP blocking** → **proxy mode's datacenter IP is fine (Y)**. Reclaim already ships a GitHub-contributions provider (proven-doable). ToS: fully clean (official API). This is the canonical low-friction, high-trust first proof.

### Codeforces / StackOverflow / LeetCode — public JSON, no auth, proxy-safe.
- **Codeforces:** `GET https://codeforces.com/api/user.info?handles=Foo;Bar` returns JSON `rating`, `maxRating`, `rank` **anonymously, no key** ([apiHelp/methods](https://codeforces.com/apiHelp/methods)). Proxy mode trivially OK. The catch for REP: anonymous endpoint means the *prover doesn't prove it's their account* unless you bind the handle to identity out-of-band (it's public data about a handle, not session-gated).
- **StackOverflow:** `GET https://api.stackexchange.com/2.3/users/{ids}?site=stackoverflow` → JSON `reputation`, `badge_counts{gold,silver,bronze}` ([SE docs](https://api.stackexchange.com/docs)). Same "public-fact, not session-bound" caveat; to prove *ownership* you'd notarize an authenticated `/me`-style call (`/2.3/me` with OAuth `access_token`). Proxy-safe.
- **LeetCode:** `POST https://leetcode.com/graphql`, `matchedUser{submitStatsGlobal{acSubmissionNum{difficulty count}}}` and `userContestRankingInfo{rating,globalRanking,attendedContestsCount}` ([discuss](https://leetcode.com/discuss/general-discussion/1797639/leetcode-api-endpoint-for-fetching-users-contest-ratings/)). Public-profile reads are unauthenticated; **own/private** data needs `LEETCODE_SESSION`+`csrftoken` cookies. JSON = durable. LeetCode sits behind Cloudflare → datacenter IPs *usually* pass for low-volume reads but can hit Turnstile under load → **conditional**.

### Strava — clean OAuth JSON, Reclaim-proven; auth friction is the only knock.
`GET https://www.strava.com/api/v3/athlete` (profile) and `GET https://www.strava.com/api/v3/athlete/activities` (activity list) return JSON over OAuth 2.0; scope `activity:read`/`activity:read_all` ([Strava reference](https://developers.strava.com/docs/reference/), [getting-started](https://developers.strava.com/docs/getting-started/)). Rate limits 200 req/15min & 2,000/day per app. **api.strava.com is a normal OAuth API — datacenter IPs pass → proxy mode OK (Y).** Reclaim ships "Strava – Last 4 Weeks Activities" (proven-doable). **Auth-friction = 3, not 5:** Strava's mobile OAuth uses a deep-link (`https://www.strava.com/oauth/mobile/authorize`) that app-switches into the Strava app, but the community documents a "very clunky" in-app-browser flow where users must re-login and "Sign in with Google/Apple" can spawn duplicate accounts and break the redirect ([communityhub](https://communityhub.strava.com/developers-api-7/use-strava-app-for-oauth2-authorization-from-web-9992)). Worth a polished native OAuth handoff. ToS: clean.

### Duolingo — durable unofficial JSON, Reclaim-proven.
`GET https://www.duolingo.com/2017-06-30/users/{id}` (resolve id via `…/2017-06-30/users?username={u}`) returns JSON with `streak`, `totalXp`, `courses[]`, etc.; supports field-selection like GraphQL (`?fields=streak,totalXp`) ([tschuy data docs](https://tschuy.com/duolingo/api/data.html), [waymobetta "tale of two APIs"](https://waymobetta.medium.com/duolingo-a-tale-of-two-apis-5313cb7aa949)). Auth = `jwt_token` cookie for private fields; much profile data is public. **Reclaim ships "Duolingo – Verify totalXp" and "Verify xp for language" providers** (proven-doable, and a hint that residential proxying was *not* required — it's on the easy list). The `/2017-06-30/` date-versioned endpoint has been **stable and alive for 6+ years**, an unusually durable "unofficial" API. ToS: grey (no official consumer API) but low-stakes and long-stable. Proxy mode: www.duolingo.com is lightly defended → **Y/conditional**.

### Anthropic Console — clean documented Admin API for spend; key-provisioning is the friction.
Spend/usage lives in JSON via the **public Admin API**: `GET https://api.anthropic.com/v1/organizations/cost_report` (USD breakdown) and `GET https://api.anthropic.com/v1/organizations/usage_report/messages` (tokens by model/workspace) ([cost_report ref](https://platform.claude.com/docs/en/api/admin/cost_report), [usage-cost-api](https://platform.claude.com/docs/en/build-with-claude/usage-cost-api)). Auth = **Admin API key `sk-ant-admin…`** (header `x-api-key`), provisionable only by org admins. api.anthropic.com is a normal datacenter-friendly API → **proxy mode OK (Y)**. ToS: fully clean (official API). **Auth-friction = 2:** getting an Admin key is a deliberate, admin-only step — much higher friction than an app-switch OAuth. The lower-friction alternative is notarizing the **console.anthropic.com session-cookie** call that the billing dashboard itself makes (cookie auth), which is grey and HTML/JSON-mixed; prefer the Admin API where the user already has a key. Proof-Value is high (verifiable real spend = strong reputation/skin-in-the-game signal), but this is a **niche population** (devs with API orgs), so it's a credibility showcase, not a volume driver.

### Spotify — **DOWNGRADE from Tier-1.** The Feb-2026 lockdown broke the easy path.
This is the biggest correction to the hypothesis. As of **Feb 6 2026**, Spotify:
- **Removed the `product` field** (subscription tier "premium"/"free") from `GET /v1/me`, along with `country`, `email`, `explicit_content`, `followers` ([Feb-2026 changelog](https://developer.spotify.com/documentation/web-api/references/changes/february-2026), [migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide)). **The clean "prove you're Premium" proof via the official API no longer exists.**
- **Crippled Development Mode:** each app capped at **5 authorized users**, **requires a Premium account**, limited to **one Dev Mode Client ID**, and a reduced endpoint set ([quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes), [TechCrunch](https://techcrunch.com/2026/02/06/spotify-changes-developer-mode-api-to-require-premium-accounts-limits-test-users/)). **Extended Quota now requires a registered business with 250k MAU** — effectively closed to us ([blog 2026-02-06](https://developer.spotify.com/blog/2026-02-06-update-on-developer-access-and-platform-security)).
- **Still available** in Dev Mode: `GET /me/player/recently-played`, `GET /me/player`, `/me/player/currently-playing` — so **listening-history proofs survive**, subscription-tier proofs do not.

**Two paths for REP, both compromised:**
1. *Official OAuth* → the 5-user cap makes a public product non-viable; only listening-history (not tier) remains.
2. *Consumer web-player token* → log into `open.spotify.com`, the `sp_dc` cookie is exchanged at `https://open.spotify.com/get_access_token` (a.k.a. the `spclient.wg.spotify.com` family) for a Bearer token with **broader permissions than the dev token** ([SpotifyScraper auth](https://spotifyscraper.readthedocs.io/en/latest/guide/authentication/)). zkTLS could notarize a call to Spotify's *internal* account-attributes endpoint to recover tier — **but this is explicitly ToS-grey and the Feb-2026 move was a deliberate anti-scraping/anti-AI lockdown**, so it's fragile and adversarial. Reclaim has a Spotify provider (proven-doable historically), but given the lockdown I'd treat Spotify as **Tier-2 "listening history only," not a Tier-1 anchor.** **Proxy mode: conditional** (Spotify is hardening; datacenter IPs on internal endpoints are risky → lean MPC/residential).

## 4. Where does proxy-mode's datacenter verifier-IP get FLAGGED? (The line.)

**The line is bot-defense posture on the *data endpoint*, not the brand.** Two clean buckets:

**Proxy mode OK (datacenter verifier-IP passes) — public/developer APIs with no behavioral WAF:**
- GitHub (`api.github.com`), Codeforces (`codeforces.com/api`), StackExchange (`api.stackexchange.com`), Strava (`api.strava.com`), Duolingo (`www.duolingo.com/2017-06-30`), Anthropic (`api.anthropic.com`), Wise (`api.wise.com`).
- These are designed for server-to-server traffic; they rate-limit by token/key, not IP reputation. **Use proxy mode (~1–2s) here.**

**Proxy mode FLAGGED → forces MPC (user residential/mobile IP) or residential proxy:**
- **Consumer-app/web surfaces fronted by Cloudflare/Akamai/Imperva/PerimeterX/DataDome with IP-reputation + TLS/JA4 fingerprinting:** Amazon (blocks most datacenter IPs on first request — [scrapfly](https://scrapfly.io/blog/posts/how-to-bypass-akamai-anti-scraping)), Uber/Lyft internal GraphQL, Ticketmaster (Imperva/PerimeterX — [scrapfly](https://scrapfly.io/blog/posts/how-to-scrape-ticketmaster)), X/Twitter, Instagram/TikTok (Arkose/DataDome), Spotify's *internal* endpoints post-lockdown.
- This is exactly why **Reclaim routes through residential connections** ("AWS/GCP/DigitalOcean ranges get flagged and blocked instantly" — [plainproxies](https://plainproxies.com/blog/residential-proxies/how-residential-proxies-help-bypass)). Their architecture choosing residential = strong signal these targets *cannot* use a naked datacenter verifier.

**A harder line — device attestation defeats BOTH proxy and MPC:**
- **Revolut retail, hardened bank apps, Instagram/TikTok mobile:** the data endpoint requires **Play Integrity / DeviceCheck / App Attest** tokens minted by a genuine unmodified app ([Guardsquare](https://www.guardsquare.com/blog/modern-mobile-api-security)). Here a residential IP doesn't help — the *device/app* must attest, which an automated zkTLS prover can't forge. **These are out of reach for zkTLS regardless of IP/mode; use official/Open-Banking APIs instead.**

**Practical rule for REP:** default to **proxy mode** for the developer-API Tier-1 set; flip to **MPC mode** (user's real residential/mobile IP, accept 3–15s) for any consumer-app surface behind a WAF; **decline** anything behind device attestation on the data endpoint.

## 5. Competitor "proven-doable" evidence (Reclaim / Primus)

- **Reclaim Protocol:** 200+ community providers, 40+ verified schemas + 240 community schemas ([github.com/reclaimprotocol](https://github.com/reclaimprotocol)). Confirmed providers for **GitHub, Spotify, Strava ("Last 4 Weeks Activities"), Duolingo ("Verify totalXp"/"xp for language"), Uber (rides), Amazon (purchase history)** ([dev.reclaimprotocol.org provider catalog](https://dev.reclaimprotocol.org/provider/details/06a8f856-c6f4-4332-abef-a6c56550fc33)). Architecture is the **attestor-as-opaque-proxy** model ([attestor-core](https://github.com/reclaimprotocol/attestor-core), ["Proxying Is Enough"](https://blog.reclaimprotocol.org/posts/proxying-is-enough)) — i.e., same IP-exposure property as TLSNotary proxy mode, and they lean on residential routing to beat the Web2 firewall.
- **Reclaim's stated reliability lesson (directly applicable):** "JSON APIs have been observed to remain relatively constant, but HTML websites often change… when an XPath changes, the provider breaks [and] can stay broken for hours, sometimes days." They now auto-fix XPath drift with Claude Sonnet ([AI to scale zkTLS](https://blog.reclaimprotocol.org/posts/zktls-ai)). **Conclusion: prioritize JSON-API targets (our whole Tier-1) and treat any HTML/XPath target (Amazon, Uber, Ticketmaster, gov portals) as a maintenance liability.**
- **Primus Labs:** browser-extension + Dev Hub "data templates"; documented sources include **Binance, TikTok, X** ([docs.primuslabs.xyz](https://docs.primuslabs.xyz/data-verification/developer-hub/)). No published exhaustive list — templates are user-created. zkFetch builds on Reclaim's zkTLS infra ([catalyst](https://projectcatalyst.io/funds/13/cardano-open-developers/zkfetch-integrating-zktls-powered-oracle-solution-for-cardano)). Less overlap with our consumer-reputation targets than Reclaim; primarily exchange/finance and social.

**Read-through:** every Tier-1 target we picked (GitHub, Strava, Duolingo) already has a *working* Reclaim provider → low technical risk. Targets that only Reclaim can do *via residential routing* (Uber, Amazon) confirm the datacenter-IP line above.
