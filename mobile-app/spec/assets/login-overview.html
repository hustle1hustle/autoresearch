Логины и proof'ы. Обзор открытий.

Что мы нашли по mobile UX для TLSNotary context proofs. Инфографика, не лонгрид.

REP · 2026-06-02 · iOS-primary · полная версия в mobile-ux-deep-research.md

Главное за 6 пунктов

  • 1
    Главная переменная не метод входа, а warm/cold юзер. Залогинен ли он уже в сервис на этом девайсе. Тёплый. быстро почти везде. Холодный. любой метод платит налог на вход.
  • 2
    Warm returning юзер реально может в 1 тап. Первый proof. 2 тапа. Второй и далее. Face ID, и proof готов за ~3 секунды. Refresh-токен GitHub в Keychain под биометрией.
  • 3
    ~1-2 секунды notarize прячутся под анимацию возврата OAuth. Pre-warm WebSocket на открытии экрана + notarize в Task.detached параллельно с iOS app-switch animation. Юзер видит "тап → done".
  • 4
    Silent warm-detection на iOS почти мёртв с iOS 9. canOpenURL только по allowlist в Info.plist (cap 50 schemes с iOS 15). Hidden WebView пробы. anti-goal violation. Что остаётся. Universal Link installability + conditional UI passkey probe.
  • 5
    TLSNotary GA mobile app пока не существует. iOS prover в экспериментальном ios-wasmtime, упирается в открытый issue wasmtime. Главный канал у них. Chrome extension. Значит REP не "побеждает" их аппку, а становится канонической мобильной zkTLS аппкой.
  • 6
    Reclaim использует WKWebView для cookie capture. Паттерн не их собственный, портируется в нативный SwiftUI. REP может взять WebView UX, оставив TLSNotary substrate.

01 Тёплый vs холодный

Один и тот же метод даёт совсем разные цифры в зависимости от того, есть ли у юзера уже живая сессия в сервисе на этом девайсе. Детект warm/cold и правильный порядок офферов важнее выбора метода.

Тёплый юзер

Залогинен в сервис на девайсе

1-3 тапа
Быстро почти везде. Passkey 3-5 сек, Sign in with Apple 1-4 сек, app-switch OAuth 5-10 сек, cookie reuse 5-12 сек. Главная преграда. iOS consent sheet, и она же единственная цена за shared cookies.
Холодный юзер

Не залогинен нигде на девайсе

+10-60 сек
К любому методу прибавляется разовый логин-подфлоу. Email + пароль, 2FA, восстановление пароля. Magic-link и email-OTP. главные сливы воронки (юзер залип в инбоксе).

03 Шесть хаков. ранжированы по impact

Каждый. конкретный трюк с измеримой экономией и ссылкой на референс-аппку. Три первых ставятся за неделю.

1

Pre-warm WebSocket на appear, не на тап

500-1000 мс с perceived latency
Открыть WebSocket к verifier и сгенерить PKCE до того, как юзер вообще тапнул CTA. Когда тапнет. сетевая часть уже оплачена. Plaid делает то же через Plaid.create() + onLoad.
Неделя 1. Тривиально. SwiftUI .task на view appear.
6

Notarize прячется в iOS app-switch animation

скрывает целые 1-2 с notarize
После OAuth-возврата iOS тратит ~400 мс на анимацию возврата в REP. В это время кидаем GraphQL + selective-disclosure proof. Юзер видит "тап → done", без отдельного спиннера.
Неделя 1. Зависит от Hack 1.
3

Pre-sheet объяснение перед iOS consent

+15-25 п.п. конверсии через системный шит
До ASWebAuthenticationSession. один экран с копией. "Сейчас iOS спросит, можно ли использовать github.com для входа. Пароль остаётся у GitHub". Системный шит теперь не пугает, юзер его ждёт.
Неделя 1. Показывать только первый раз, потом флаг в UserDefaults.
4

Universal Link auto-return. никаких custom URL schemes

убирает "swipe-back" drop ~30%
OAuth callback URL = Universal Link с apple-app-site-association. iOS сам маршрутизирует обратно в REP. Никаких "Open in REP" кнопок, никакого ручного переключения. Плэйд делает только так.
Неделя 1. AASA файл + entitlement.
2

Refresh token + Face ID в Keychain. 2→1 тап на повторе

~7с → ~3-4с на каждом repeat proof
После первого proof кладём refresh token в Keychain под .biometryCurrentSet. Второй proof. Face ID запускает silent refresh-grant + notarize. Нет app-switch'а, нет consent'а. Apple Wallet делает это с issuer-app credentials.
Неделя 2. GitHub OAuth refresh + SecAccessControl.
5

Conditional UI passkey probe

3-5с вход когда применимо
mediation="conditional" фоном проверяет наличие passkey без UI. Если есть. появляется в системной autofill-полоске одним тапом. Privacy-preserving by design. RP не узнаёт, есть ли passkey, если юзер сам не выбрал.
Неделя 3. Применимо для REP-self login и cookie-таргетов (Duolingo, LeetCode когда выкатят).

05 Что украсть у других аппок

Каждая. что украсть и чего избегать. Чистый паттерн-grab без копирования.

Аппка Что они делают Что украсть Чего избегать
TLSNotary
Chrome ext		 Десктоп. side-panel, переключение между табами для логина и notarize. GA mobile аппки нет. Transparency about commitments в success state. Показать, что в proof спрятано. Десктоп-парадигма. tab juggling не переносится в мобайл.
Reclaim
InApp iOS SDK		 SwiftUI sheet с WKWebView внутри. Логин внутри шита. Cookie capture через WebView API (включая HttpOnly). Inline WebView login для cookie-таргетов. Юзер не покидает аппку. WKHTTPCookieStore + WKUserScript паттерн. Тяжёлый Reclaim-брендинг во время чужого логина. Бренд таргета должен доминировать.
Plaid Link
gold standard		 Preload через Plaid.create(), потом .open(). OAuth handoff через Universal Link. Event-driven UX. Preload-паттерн (Hack 1). Универсальные линки вместо схем (Hack 4). Event sequence для инструментирования каждого drop-off. Слишком тяжёлый брендинг сам по себе подходит для финансов, не для low-stakes proof'ов.
Stripe Identity
multi-step		 IdentityVerificationSheet. Document capture (auto, без shutter) → selfie → loading → success. Auto-capture без manual shutter. Один шит с несколькими шагами, не navigation stack. Implicit progress без церемонии. Оптимистичное "All set!" до фактической проверки. У нас 1-2с notarize короче, показывай реально.
Apple Wallet
native fast		 "Add to Apple Wallet" → PassKit берёт управление → ~3 системных экрана → Face ID → success + push. Skip extra auth когда уже auth'ились в issuer app (OTP при install). Success notification вне флоу. Не интерстициалить системные хендофы. Запрещено иметь interstitials между Apple-button и системным шитом. Применимо и к OAuth.
Privy / Web3Auth
crypto Web2-feel		 useLoginWithPasskey hook с явным state machine (initial → generating-challenge → awaiting-passkey → submitting-response → done). Explicit auth-state машина в UI. Разные copy на разных стадиях, никаких "Loading…". REP-аналог. connecting / auth / notarizing / done. Огромный modal с веба, не переносить на мобайл.

06 iOS vs Android. где разница реальная

По таймингам почти симметрично. Но есть три места, где платформы расходятся, и Android обычно выигрывает за счёт меньшего количества системных шитов.

iOS

  • ASWebAuthenticationSession. шарит куки с Safari, НО показывает scary consent sheet каждый раз. Нельзя убрать без потери шаринга.
  • canOpenURL. только по allowlist (LSApplicationQueriesSchemes), cap 50 с iOS 15.
  • SMS код. Security Code AutoFill через QuickType, ~3 мин окно, нужно слово "code" в сообщении.
  • Passkey. ASAuthorizationPlatformPublicKeyCredentialProvider, conditional UI с iOS 17.5+, requestStyle:.conditional.
  • Universal Links. apple-app-site-association в /.well-known/, Associated Domains entitlement. TestFlight иногда тупит на 15 минут с fetch'ем AASA.
  • Биометрия. Keychain + SecAccessControl(.biometryCurrentSet). Re-enrollment Face ID = item инвалидируется (security feature, не баг).

Android

  • Chrome Custom Tabs. шарят cookie jar с Chrome БЕЗ всякого consent sheet. Тихий cookie reuse. iOS-эквивалента нет.
  • PackageManager queryIntentActivities. <queries> в манифесте с Android 11+. Тот же allowlist, что в iOS.
  • SMS Retriever API. сам подхватывает код без permission и без копи-паста. Чуть быстрее iOS.
  • Passkey. CredentialManager.getCredential с GetPublicKeyCredentialOption + isConditional=true. System autofill bar с Android 14+.
  • App Links. assetlinks.json + android:autoVerify="true". Аналог UL, та же логика.
  • Биометрия. EncryptedSharedPreferences + BiometricPrompt. Эквивалент iOS.

Чистая разница в пользу Android. Hack 3 (pre-sheet объяснение) на Android можно вообще не делать. Custom Tabs тихо шарят куки. На iOS pre-sheet обязателен.

07 Чего не делать. anti-patterns

То, что убивает воронку в каждой второй аппке. Каждый. что выглядит, и как фиксится.

⏳
"Spinner without context"
Generic ProgressView() с надписью "Loading…" или без копии.
Каждое ожидание называет шаг. "Confirming with notary…". Стадии через ✓ / ● / ○. Никогда не "Loading".
❓
"Did it work?"
Тихий успех. модал закрылся, юзер вернулся на исходный экран без подтверждения.
Явный success state с фактом ("octocat · 1,234 contributions"). Опционально local push с подтверждением (Apple Wallet паттерн).
📧
"Lost in inbox"
Magic-link флоу. юзер тапает линк в Mail, открывается Safari, REP остался в фоне.
Anti-goal. magic-link никогда не primary/secondary. OTP-код, который виден в push, без открытия Mail.
↩️
"Where did I come from"
После OAuth юзер на callback-странице в Safari без явной кнопки "вернуться".
Universal Link auto-return (Hack 4). Никогда custom URL schemes. iOS сам маршрутизирует.
😱
"Scary system sheet"
Юзер тапает "Continue with GitHub" и получает в лоб iOS-шит "App wants to use github.com to Sign In", которого он не ждал.
Pre-sheet объяснение (Hack 3). Показывается один раз, потом флаг в UserDefaults.
🔍
"What was just proved"
Proof готов, но юзер видит только зелёную галочку. Что доказано, что спрятано, кто атесторил. неясно.
Раскрываемая карточка "What was proved" в success state. Реальный request, revealed fields, redacted bytes, ключ нотариуса, expiry.
🔄
"Re-prove every time"
Каждое обновление proof'а. полный 2-тап OAuth заново.
Hack 2. refresh token + Face ID. Second proof и далее. 1 тап, ~3 секунды.
🎭
"App-switch ты не можешь верить"
Юзер бросается на какую-то OAuth-страницу, URL bar скрыт, неясно. github.com или наш скам.
НИКОГДА WKWebView для password entry на чужих сайтах. Только ASWebAuthSession (показывает URL) или app-switch. Apple HIG требование тоже.
🏷️
"Branded sheet on third-party login"
Тяжёлый REP-брендинг во время ввода GitHub-пароля. Юзер не понимает, кому он даёт credentials.
Во время OAuth handoff бренд таргета доминирует. REP chrome subtle. REP возвращается только в success state.
🚪
"Permission requested before purpose"
"Allow notifications?" / "Allow Face ID?" prompts на первом launch до того, как юзер что-то сделал.
Биометрия. запрашиваем когда юзер реально её используем (перед сохранением в Keychain). Push. после первого успеха ("Want a heads-up when…?").

11 Когда нужно много данных. Multi-endpoint proof'ы

Один proof не всегда = одно число. Для богатого контекста (музыкальный вкус, спортивный профиль, dev fingerprint) нужно дёрнуть несколько endpoint'ов с одной платформы. Хорошие новости. TLSNotary это умеет нативно через одну TLS-сессию.

Три размера задачи "много данных"

Size 1
Большой JSON от одного endpoint
✓ почти бесплатно
Spotify /me/top/tracks с 50 треками. Strava /activities со 100 записями. Proxy mode почти flat по payload (1KB→51KB поменяло время с ~1.6с до ~1.6с в бенчмарках). MPC mode тоже почти flat благодаря defer_decryption.
Size 2
Много endpoint'ов одной платформы
✓ одна TLS-сессия
Spotify-кейс. Открываем одну TLS-сессию к api.spotify.com, дёргаем 5-6 endpoint'ов последовательно или pipelined, нотарь подписывает весь transcript. Один attestation, один Merkle root, selective reveal по byte-range'ам. ~2-4с в proxy mode.
Size 3
Кросс-платформенная композиция
⚙ задача Proof Graph Runtime
"Я serious dev" = f(github.contributions, stackoverflow.reputation, leetcode.rating). Каждая платформа = отдельный proof, отдельная сессия. Композиция считается на стороне REP без новой минтинг-сессии. Это compounding moment графа.

ONE Attestation. Merkle root над всем transcript'ом

Selective reveal по byte-range'ам. Раскрываем 6 групп response-fields (top_artists, top_tracks, recently_played, playlists, following, identity). Redact 6× Authorization: Bearer … в request-bytes. Один signing key, одна подпись нотаря, одна VCC с 6 фактами внутри.

Рычаги в TLSNotary: MpcTlsConfig::max_sent_data / max_recv_data декларируем заранее (TLSNotary preprocess'ит circuit под этот размер). defer_decryption=true по дефолту. response декриптится локально после close, без MPC overhead. ProveConfig's reveal_sent/reveal_recv принимают несколько byte-range'ов, так что многократный redaction в одном transcript'е работает из коробки.
